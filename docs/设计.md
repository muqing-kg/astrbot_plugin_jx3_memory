# 设计

## 一、目标与反目标

目标：模型像在这个游戏里待过很多年。聊天里冒出一个剑网3 的词，它知道那是什么，用玩家的话接下去。

反目标（做出来就是失败）：

- 不做问答命令、不做关键词触发、不抢消息。
- 不在回复里写"以下是检索到的资料"、"根据资料显示"、"资料库中无此条目"。
- 不要求模型逐条标注出处编号——那正是工具感的来源。
- 不给人格设定。主人另有单独的人物设定，插件只提供事实。
- 查不到就用人话搪塞（"记不太清了"），不暴露机制。

## 二、触发与检索

不预先灌输，改成按需查：模型要回话时，拿当前消息和最近几条历史去碰词表，碰到才给。

- 匹配是**字面**的：首字分桶 + 子串判定，长词优先。不用向量——向量召回不准时塞错资料比不塞更糟，而实测漏检的头号原因是词表不全，不是算法。
- FTS5 用不了（实测）：`trigram` 对两字中文词恒 0 命中，`unicode61` 把整句当一个 token。
- 多段文本之间用分隔符隔开再匹配，避免上段结尾与下段开头拼出并不存在的词。
- 词表是 `entry` 的 name 加 `term` 里的别名，命中别名归一到主名（"跳车"→"跳车狗"）。别名不收，聊天里的简称就接不住。
- 同名跨类型只留一个，顺序：门派 > 心法 > 技能 > 副本 > 首领 > 奇遇 > 通识 > 成就 > 任务 > 公告 > 物品。
- 两字名在物品、任务、成就里不进词表——"长安""龙渊"这类既是地名也是任务名，注进去比不给更糟。

## 三、注入

落点是 `req.extra_user_content_parts`，每块 `mark_as_temp()`：只对本次请求生效，不写进对话历史，也不改 `system_prompt`（改了每轮必破前缀缓存）。

文风：

```
（你玩了很久剑网3，下面这些是你本来就知道的东西。用得上的时候用自己的话说，
不要照抄，也不要提「资料」「条目」这类词。没提到的说明你不清楚，别猜。）

· 黑工：周常副本只能打一次，后面重置CD打的就算黑工……
```

- 第一人称记忆口吻，不编号、不标来源、不提示条数。
- 每条摘要 60 字以内，按句读收口，不留半句。
- 双闸门预算：条数上限 5、字数上限 1200，任一先到即停。
- 同一会话连续几轮命中同一批条目时不再重复注入；换会话或命中集合变化才重新给。
- 命中为空就一个字都不加，绝不注入"没有找到相关信息"。

## 四、存储

SQLite 单库 `data/memory.sqlite3`（58.9 MB），零第三方依赖。

- `entry(id, kind, name, brief, meta, body)`，`(kind, name)` 唯一。
- `term(word, entry_id)`：主名与别名混存，检索时全部装进内存词表。
- 词表在插件启动时一次性装好，之后每次请求只走内存匹配，不查库。

## 五、验收

- 问"碎银怎么换通宝"→ 答对，且不出现"根据资料"。
- 闲聊里提到"荒血路"→ 自然接一句副本信息，不需要被问。
- 问一个库里没有的东西 → 用玩家口吻说记不清，不报错、不提资料库。
- 寒暄句（"今天晚饭吃啥"）零注入。
- 连续 20 轮对话，注入总量不超过预算，同批内容不重复堆叠。

## 六、与提醒插件的边界

两个插件各自抓一份公告：提醒插件为抽活动排期，本插件为"最近有什么活动"这类记忆。重复的是 HTTP 请求，换来故障隔离——一边坏了不影响另一边。本插件不读对方数据库。

两个插件都挂 LLM 钩子时安全：同类型钩子全部执行、改同一个 `req`、改动叠加，没有截断机制。
